# QyBit W2：FLAC 码流之后的数据（文件末尾的 ID3v1 标签、填充）

遵循根目录 AGENTS.md。来源：2026-11-10 仓库检查发现，用户 2026-11-11 同意修改。

状态：已完成（2026-11-11）。实现在 `qy-codec-flac`（`FlacDecoder::trailing_data`），记录见 [docs/m1-t2-flac.md](../docs/m1-t2-flac.md) 的“码流之后的数据”。

**现象**：标签软件会在 FLAC 文件末尾附加 ID3v1 标签（128 字节，以 `TAG` 开头），有的写入程序在末尾留下填充。此前这样的文件全部样本播完之后，解码器在这些字节上找不到帧同步码，以 `LostSync` 失败：该曲目记为失败，播放列表按出错策略停止，下一首不播，命令行退出码为 1。

**原则**（同 W1）：只在意图没有歧义时处理；不改、不编造样本；处理要报告；有歧义的照旧报错。

## 1. 规则

| 情形 | 处理 |
| --- | --- |
| STREAMINFO 声明了总样本数（非 0），已解码的样本数恰好等于它，其后的字节解不出一帧（同步码不符、帧头或帧尾校验不过，或到源结束、输入窗口装满仍凑不成一帧） | 码流按自己的声明已经完整：其后的字节不属于码流，不读取；曲目正常结束，报告写明 |
| 同上，但其后是一个有效的帧（实际样本多于声明） | 照旧解码，结束时以 `TotalSamplesMismatch` 报错 |
| 总样本数为 0（未知），其后的字节解不出帧 | 无从判断音频是否完整，照旧按码流错误报告（如 `LostSync`） |
| 总样本数尚未解满时遇到解不出帧的字节 | 照旧按码流错误报告；不做失步重同步 |

依据：

- RFC 9639 §8.2：STREAMINFO 的总样本数是“码流中声道间样本的总数”，0 表示未知。解满这个数之后，码流按自己的声明没有更多音频。
- libFLAC 1.3.4 `stream_decoder.c` 的 `frame_sync_`：已知总样本数且已解满时直接进入流结束状态，注释写明“例如避免在 ID3V1 标签上找同步”。libFLAC 1.4 起去掉了这项检查，改为继续找同步码并给出一次 `LOST_SYNC` 错误状态，读到源结束后同样进入流结束状态。两种做法交给应用的样本相同，差别只在是否报告一次同步丢失。本解码器取前者的判断条件，并把这件事写进报告。
- 规范没有定义码流之后可以有什么；因此只在“声明的总数已解满”这一条件下处理，不识别具体的标签格式，对所有文件按同一规则。

## 2. 报告

- 解码器：`FlacDecoder::trailing_data()`，`AutoDecoder::trailing_data()`。
- 播放器与命令行：`qy_player::Diagnostics::end_notes`（新增，带默认实现，不破坏已有实现）在关闭曲目时给出一行说明；`qybit decode` 同样输出。
- 嵌入式宿主暂不输出这条说明（曲目同样正常结束）。

## 3. 验收

- `crates/qy-codec-flac/tests/trailing.rs`：
  - ID3v1 标签、零填充、单个字节、同步码的前半、伪同步码、一帧的前 100 字节：样本与不带尾部数据的同一文件逐个相同，正常结束并标记；按 1、7、4096 字节（一帧的前 100 字节为 1、333 字节）分块与一次全部喂入的结果相同；复位后标记清除；
  - 窗口装满仍凑不成一帧的情形；对照：总样本数未解满时同一帧仍按容量不足报告；
  - 三种意图不明的情形照旧报错（总样本数未知、其后是有效帧、码流中途）。
- `qy-player` 的 `trailing_tag_after_flac_stream_does_not_stop_the_playlist`：带标签的 FLAC 之后的下一首照常播放，设备字节等于 libFLAC 参考样本加下一首的数据，实时输出含说明。
- 原有 FLAC 测试（含 `total_samples_checked_at_end`）不改动，全部通过。
